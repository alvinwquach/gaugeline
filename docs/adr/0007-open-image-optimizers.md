# ADR-0007: Open image optimizers: read the config by default, probe only with consent and an address you chose

Status: proposed Date: 2026-11-11

**STOP: waiting for the owner's decision; no check is built.** This record proposes; it changes no
code, no flag and no line of CLAUDE.md. Nothing in XF-04 is implemented until the owner accepts one
of the options below (or another). Branch `xf/image-optimizers-adr`.

## Context

A site that resizes images on the server has a URL that fetches an image from an address in the query
string, re-encodes it and sends it back. If the list of allowed sources is missing or too wide, that
URL fetches and re-serves any image on the web for anyone who asks. The effects on the owner are
bandwidth and compute cost (the platform bills for optimization), a cache that fills with other
people's images, the site's own name on an open relay, and, depending on the stack, a server that can
be made to request an address it can reach and the public cannot (server-side request forgery, SSRF).

The optimizer addresses XF-04 names, and what each documents as its allowlist:

| Stack             | Address                       | Allowlist setting                                                                  | Source   |
| ----------------- | ----------------------------- | ---------------------------------------------------------------------------------- | -------- |
| Next.js           | `/_next/image?url=&w=&q=`     | `images.remotePatterns` (`images.domains` is deprecated)                           | [docs] 1 |
| Vercel (any)      | `/_vercel/image`              | `images.remotePatterns` / `domains` in the build output; 404 with none             | [docs] 2 |
| Nuxt Image (IPX)  | `/_ipx/`                      | `domains` (and `alias`) in the module options                                      | [docs] 3 |
| Astro             | `/_image?href=`               | `image.domains` / `image.remotePatterns`                                           | [docs] 4 |
| Netlify Image CDN | `/.netlify/images?url=`       | `images.remote_images` in `netlify.toml` (regular expressions)                     | [docs] 5 |
| Cloudflare        | `/cdn-cgi/image/<opts>/<src>` | "Sources" (allowed origins) in the dashboard; the zone's own images always allowed | [docs] 6 |

What the documentation says, as far as it could be read (see "Sources and what could not be read"):

- Next.js: a protocol or hostname that matches no `remotePatterns` entry answers `400 Bad Request`.
  `*` matches one path segment or subdomain, `**` any number; leaving out `protocol`, `port`,
  `pathname` or `search` widens the match and the docs say that is not recommended for security.
  [docs] 1. That a bare `*` hostname matches every host is claimed by one third-party post and is
  **uncited** here.
- Vercel: with no `images` block in the build output, `/_vercel/image` answers `404`. [docs] 2.
- Astro: authorization covers `<Image />`, `<Picture />` and the image helper; a URL that matches
  neither `image.domains` nor `image.remotePatterns` raises a "remote image not allowed" error; a
  `remotePatterns` entry with only `protocol: "https"` permits every HTTPS host. [docs] 4. How the
  `/_image` endpoint itself answers is **uncited**.
- Netlify: a remote source must be allowlisted in `netlify.toml`; the URL in the request is
  percent-encoded; credential headers are not forwarded to the remote host. [docs] 5. The status for
  a non-matching address (one third-party page says 404) is **uncited**.
- Cloudflare: by default only allowed origins are accepted and the zone's own images always are;
  an origin entry may carry a path prefix; the check applies to the first URL only, so a redirect
  that leaves the zone is followed and the result transformed. [docs] 6.
- Nuxt Image / IPX: the module documents `domains` and `alias` for the production `/_ipx` endpoint.
  [docs] 3. The exact behaviour of the endpoint for an unlisted host is **uncited**.

History worth knowing, from advisory aggregators only (the primary advisories could not be opened
from this environment, so treat each as a lead to confirm before quoting it anywhere):

- CVE-2025-59471 (Next.js self-hosted Image Optimizer: a remote image is loaded into memory with no
  size limit, a denial of service when `remotePatterns` allows it). Secondary source [adv] 7.
- An unanchored allowlist regular expression generated by the Astro Netlify adapter (an allowed
  origin appearing anywhere in a URL satisfied the check; fixed in `@astrojs/netlify` 8.2.4).
  Secondary source, no advisory id read [adv] 8.
- A Nuxt Image / `ipx` security fix (patched in `@nuxt/image` 1.11.2 or 2.2.1, `ipx` 2.1.2, 3.1.3 or
  4.1.0), named only in a vendor changelog, the advisory itself not read [adv] 9.
- Several further CVE numbers for Next.js image optimization appeared in search results from
  low-trust sites. They are **uncited** and not repeated here.

The pattern across all of it: the optimizer is safe only as far as its allowlist is, and the
allowlist is the thing that is wrong in practice (a wildcard added to "make images load", a
`domains` list that grew, a regular expression that was not anchored).

### The problem for Gaugeline

To prove an optimizer is open, Gaugeline would have to send `GET /_next/image?url=https://<outside
host>/x.png&w=64&q=50` to the site and see the answer. That is a `GET`, so rule 6 is met in the
letter. It is not met in spirit, and rule 14 is the rule that bites:

1. It makes the checked site's server request a third party on Gaugeline's behalf. The third party
   and the owner's bandwidth are both affected, and a cache entry is created on the site.
2. It is shaped like an attack payload. An open-proxy or SSRF test is exactly this request, and
   rule 14 says "No attack payloads", and that "Active security testing is delegated to tools built
   for it (OWASP ZAP baseline, Nuclei) and their results imported".
3. The usual thing a probing check does (rule 14) is ask a non-public path or use a site's own key.
   This one asks a public path to do work. It is a new kind of probe: **it makes the site act
   outward**. The rule does not name it today.

There is also a trap in the proof itself. A `200` is a proof of "open" only if the host in `url=` is
not in the allowlist. The site's own host is always allowed (Cloudflare says so for its zone, and
the other stacks allow the host the owner uses for images). Gaugeline cannot know the allowlist
without the config. So a probe that does not know the allowlist can answer "it fetched" and mean
nothing.

What exists on main today: no import of ZAP, Nuclei or SARIF results anywhere in `packages/*/src`
or `docs/` (searched for `zap`, `nuclei`, `sarif`, `owasp`; the only hit for "zap" is a Zapier
webhook line in `docs/notifications.md`). The image parser (`packages/core/src/checks/images/refs.ts`)
already reads `/_next/image` addresses from a page; nothing reads `/_ipx/`, `/_image`,
`/.netlify/images`, `/_vercel/image` or `/cdn-cgi/image/`. Probing checks today
(`gated-download-open`, and two others, see docs/options.md) run only with `--owner-consent` or a
`gaugeline.consent.json` that records who agreed and when
(`packages/core/src/consent.ts`).

## Decision

Proposed, for the owner to accept, change or refuse: **A as the always-on part, C as the opt-in
proof, D noted as the route for anyone who wants more.** B is not recommended.

### A. Passive: read the page, and the config if the owner gave it (always on, no new request)

Two parts, both look and never poke:

1. **From the page alone.** Detect that an optimizer is in use and which one, from the addresses the
   page already names (`/_next/image`, `/_ipx/`, `/_image`, `/.netlify/images`, `/_vercel/image`,
   `/cdn-cgi/image/`), and list the remote hosts those addresses already carry in `url=`/`href=`.
   Gaugeline sends no request to the optimizer. What this can say: an optimizer exists, and these
   hosts are at least in its allowlist. What it cannot say: whether the allowlist is closed. It
   says so, as "could not be checked" (existing `couldNotCheck`, no finding):

   > could not be checked: this page resizes images through `/_next/image`, and whether that
   > address fetches only the hosts you listed is not visible from the page. Give Gaugeline the
   > `images` settings of your framework, or run the probe on a site you own.

   (Whether a built client bundle exposes `images.remotePatterns` is **uncited** and must be
   checked in the build, not assumed.)

2. **From the framework's settings, if the owner gave them.** A path to the file
   (`next.config.*`, `nuxt.config.*`, `astro.config.*`, `netlify.toml`) or, for the git adapter, the
   repository. Gaugeline reads it as text and looks for: a wildcard hostname (`*`, `**`,
   `**.com`-style), a `domains` or `allowed` list that contains a wildcard, a `remote_images` regular
   expression that is not anchored, an `https`-only pattern with no hostname, a missing hostname
   with a present optimizer.
   This is a statement about the file, so it is certain: "your settings allow any host", not "your
   site is open".

Findings (names proposed, severity high unless said):

- `image-optimizer-allowlist-wide`: "Your image settings let the image address fetch from any
  website". Evidence: the file, the line and the entry. Fix: list the exact hosts.
- `image-optimizer-allowlist-unanchored` (medium): a Netlify `remote_images` pattern that is not
  anchored with `^` and `$` (the regular expression is tested for a match anywhere in the URL).
- Nothing at all when the settings are tight. When the optimizer is present and no settings were
  given: the "could not be checked" line above.

### C. Opt-in proof: `--owner-consent` plus a test address the owner chose

The proof exists, behind two things the owner has to do, both explicit:

- `--owner-consent` (or `gaugeline.consent.json`). This is the existing probing family, not a new
  flag, because the owner already has one place that says "I may test this site", with who and
  when, and a second consent switch would be two places to forget. The probe is therefore a
  probing check by rule 14 and carries the same documentation line: "run only on sites you own or
  have permission to test".
- A test image address the owner controls, in a new settings file `gaugeline.images.json` as
  `imageOptimizerProbeUrl` (an `https` address of a public host; never an IP literal; never a
  private, loopback or link-local address, which the fetcher would refuse anyway and which would be
  an SSRF test, see B). No address, no probe: the run says "could not be checked: no
  `imageOptimizerProbeUrl` set" and nothing is sent. Gaugeline never chooses the target.

Rules of the probe, all enforced in code and tests if accepted:

1. **One `GET` per optimizer found on the page**, to the site's own origin, through the fetcher,
   with `url=<the owner's address>` and the smallest width and quality the optimizer accepts (the
   values its own configuration lists; Gaugeline does not guess them, and if it cannot tell which
   are accepted the answer is "can't tell"). Never more than one request per optimizer address; at
   most six per run. No retry.
2. **No redirect is followed.** A `3xx` is "can't tell".
3. **The body is never stored, logged, printed or hashed beyond the first bytes.** Read at most
   1,024 bytes to see whether it is an image (`image/*` content type and a known signature), then
   close. The query string is never printed (the way `gated-download-open` handles it).
4. **The probe host must not already be allowed.** Before sending, the run refuses if the host
   equals the site's own host, equals any host the page's optimizer addresses carry (known to be
   allowed), or, when settings were given under A, matches the allowlist found there. Why: a `200`
   from an allowed host proves nothing. Gaugeline cannot see a hidden allowlist, so the docs say:
   "choose an address on a host that is not one of your image hosts", and that is also why the owner
   picks the address (Gaugeline cannot pick one that is certain to be outside).
5. **Cache.** The optimizer creates a cache entry on the site for the exact `(url, w, q)` it was
   asked. The probe uses one fixed query, so repeat runs hit the same entry and create no new one
   after the first. Gaugeline does not add a cache-busting parameter (a random one would make every
   run a new fetch of the owner's image and a new entry). The cost is stated in the docs: "one
   small cache entry per optimizer".
6. **Every request appears** in the Pages checked view and the saved requests file with the
   optimizer address and no `url=` value beyond its host.

Answers and the exact words:

| Answer to the probe                                                                                                 | Result                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `200` and an image of the owner's file                                                                              | **Finding** `image-optimizer-open` (high): "Your image address fetched an image from a website you did not list. Anyone can use your site to resize and serve images from any address." |
| `400`, `403` or `404`                                                                                               | Pass (the optimizer refused an unlisted host). No finding.                                                                                                                              |
| `200` that is not the owner's image (an HTML page, a placeholder), `3xx`, `5xx`, a timeout, a body too large, `429` | "could not be checked: the optimizer answered `<status>`, which does not say whether it is open"                                                                                        |
| The probe address is refused (host already allowed, not `https`, private)                                           | "could not be checked: `<reason>`", nothing sent                                                                                                                                        |

The word is "open" only in the one row where the optimizer returned the owner's file from a host
the run could show was not in the page's own list. "Can't tell" is the default for everything else.
There is no `error`-level result for a `5xx`: a server that fails on a fetch has said nothing about
its allowlist.

### D. Noted: import, do not generate

The tools rule 14 names already test this (ZAP and Nuclei both have open-redirect and SSRF-style
templates; the exact template ids are **uncited**). There is no import surface on main (see
Context), so D today is a documentation line ("for an active test, run Nuclei and ZAP and read the
result next to this report"), not a feature. An importer (SARIF or Nuclei JSONL into findings) is a
larger separate decision with its own record: it would define what an imported finding means when
Gaugeline did not make the request, and is out of scope here. If the owner prefers D to C, XF-04
ships A only and this record's section C is dropped.

## Alternatives

### B. Opt-in flag with a Gaugeline-chosen neutral address (`--probe-image-optimizer`)

One `GET` per optimizer with a fixed harmless outside address, no flag value from the owner. The
options for that address, and why each loses:

- **A tiny static image on a domain Gaugeline owns.** Lost: the optimizer's server would call that
  domain on behalf of every checked site, so its owner would learn which sites are being checked and
  when. That breaks ADR-0003 (no telemetry, nothing sent) in spirit and adds an availability
  dependency to a check (the domain down means "can't tell" for everyone). Not acceptable by
  default.
- **The checked site's own origin by an alternate host name** (`www.` against bare, `127.0.0.1`
  through a Host header, a different port). Lost: the site's own host is allowed by design
  (Cloudflare documents it; the others allow the owner's image host), so a `200` proves nothing, and
  the cases that do not prove nothing are the next item.
- **A `data:` URL.** Lost: harmless, but the stacks reject it for reasons unrelated to the
  allowlist, so a refusal is not evidence of a closed list and acceptance is not evidence of an open
  one. It tests nothing useful.
- **A loopback, private, link-local or metadata address** (`127.0.0.1`, `169.254.169.254`).
  Lost, hard: it is an SSRF payload by definition. It would ask the site's server to reach into its
  own network. Rule 14 forbids it, and no consent switch changes that: consent covers testing a
  site's own public behaviour, not aiming its server at a metadata service.
- **A well-known third-party image** (a public placeholder or CDN image). Lost: it loads someone
  else's server on every run and fails when they change it, and a stack that allows that one host
  looks closed.

Lost overall because every Gaugeline-chosen address is either a privacy leak, a payload, or a proof
that proves nothing.

### D alone (do not build)

Ship nothing for XF-04; point at Nuclei and ZAP. Lost as the only answer: it leaves the common,
cheap and certain case uncovered (a wildcard in a settings file, which needs no request at all), and
most of the audience (freelancers on Next.js and Vercel for small businesses) will not run a second
tool. Kept as the note under C.

### Config check as a finding "open" from the page alone

Report an optimizer found on the page as a finding ("your image address may be open"). Lost: a
finding that is true for every Next.js site on earth is noise and teaches the owner to ignore the
tool. Rule 7 says the same input gives the same findings; the page gives no evidence either way, so
the honest result is "could not be checked".

### A single new flag instead of reusing `--owner-consent`

A separate `--probe-image-optimizer`. Lost: one more consent surface to keep in step with
`gaugeline.consent.json`, and a second place a reviewer has to look for "who agreed". The cost of
reusing the family is that someone who consents to download-route probing also consents to this
probe; the settings file makes the second step (choosing an address) explicit, so consent alone
never sends it.

## Cost

- A is weaker than a proof: from the page alone it cannot say "open", only "present, not checked",
  and with settings it reports the file, not the running site (a site can deploy a different file
  than the repository holds).
- C sends a request that makes the owner's server fetch an address: one small bandwidth cost, one
  cache entry per optimizer, and a line in the owner's access log. The docs say so before the owner
  runs it.
- C relies on the owner choosing a host that is not allowlisted. Gaugeline can refuse the obvious
  mistakes (the site's own host, the page's own image hosts, a host the given settings allow) and
  cannot refuse the rest. A `200` the owner caused by choosing an allowed host reads as "open"; the
  wording of the finding names the address that was used, so a reviewer can see it at once.
- `image-optimizer-open` is a probing check, so it is off in default runs and in CI templates unless
  consent is given. The common run reports "could not be checked" for the optimizer, and that line
  must stay in the report (not be dropped) so the gap is visible.
- Rule 14's definition of a probing check needs one clause (below), a change to a binding rule.
- Six optimizer stacks mean six sets of answers to keep current as vendors change status codes
  (the table above has three behaviours that are uncited today).
- If accepted, a new settings file (`gaugeline.images.json`) and, under A, a way to hand Gaugeline a
  framework settings file, both documented in docs/options and tested for the match with `--help`
  (rule 9).

## What would change it

- The owner prefers B with a Gaugeline-owned address: it would need its own record that revisits
  ADR-0003 and who runs the address.
- A vendor documents a read-only way to ask "is this host allowed" (a dry-run or a status endpoint).
  Then no outside address is needed and the proof becomes a plain read.
- The built client bundle of the common stacks exposes the allowlist: then A alone could say "open"
  from the page for those stacks, and C would matter less.
- A primary advisory shows the allowlist check itself is bypassable (as the Astro Netlify regular
  expression was): then reading the config is not enough, and a probe with a second, deliberately
  different address would be argued for (still one request per address).
- An importer for Nuclei or SARIF results lands (a separate record): then D becomes a feature and C
  could be dropped.

## If accepted: what changes

- **CLAUDE.md rule 14** gets one sentence: "A request that makes the checked site's own server fetch
  an address Gaugeline or the owner names (an image optimizer's `url=`) is also a probing check:
  off by default, enabled with `--owner-consent`, and the address is chosen by the owner, never by
  Gaugeline, never a private, loopback, link-local or metadata address." Rule 6 is unchanged
  (the request is a `GET` through the fetcher to the site's own origin).
- **This record** moves to `accepted` (the Decision lines for B, or the half of C and D that the
  owner refuses, are edited out before that, since a record is not edited once accepted).
- **docs/adr/README.md** row for 0007 changes from `proposed` to `accepted`.
- XF-04 becomes buildable: `image-optimizer-allowlist-wide`, `image-optimizer-allowlist-unanchored`
  (A) and `image-optimizer-open` (C, probing), their entries in the checks reference, the
  `docs/options` and `--help` lines for the settings file, a privacy page section "Image optimizers
  (a probing check)" listing exactly what is sent, a changeset (minor), and a `PROGRESS.md` row.
- A fresh `pnpm surface` update for the new check ids.

## Tests required if built (listed first, rule 5)

- Unit: an optimizer-address parser for all six address shapes (encoded and unencoded `url=`,
  `/cdn-cgi/image/<opts>/<src>` where the source is not encoded); a settings reader for the four
  config shapes, covering a wildcard host, an `https`-only pattern, an unanchored regular
  expression, a missing hostname; the answer table above, one row per case.
- Integration (invented fixtures, a fixture server on `127.0.0.1` with `allowPrivate`): a Next.js
  fixture with `remotePatterns: [{ hostname: "**" }]` produces `image-optimizer-allowlist-wide`; a
  tight one produces nothing; a page with an optimizer and no settings produces the "could not be
  checked" line and **zero** requests to the optimizer address; an open fixture optimizer under
  consent plus an address returns exactly one `GET` per optimizer and the `image-optimizer-open`
  finding; a closed one (`400`) passes.
- End to end: the CLI with `--owner-consent` and the settings file; the report names the address
  used; without consent nothing is sent, with a count of requests asserted from the fetcher history.
- Edge cases: the probe address is the site's own host (refused, nothing sent); is a host the page
  already uses (refused); is `http`, an IP literal, `127.0.0.1`, `169.254.169.254` (refused); the
  optimizer redirects (not followed, "can't tell"); answers `200` with HTML (not "open"); answers a
  body larger than 1,024 bytes (read stops, connection closed); two optimizers on one page (two
  requests, never three); a run repeated (the same single query); the query string never appears in
  the log, the report or the saved requests file; the key-and-secrets scan finds nothing.
- Promise test: with consent off, the request history of a full run holds no request whose query
  contains `url=http` pointing off the site (the same style as the download-route promise test).
- CI matrix: Node 22 and 24.

## Enforced by

Nothing new, because nothing is built. What already holds, and what a built version would sit on:

- `packages/core/src/fetcher.ts` (every request to a checked site is a `GET` or a `HEAD`; private,
  loopback, link-local and metadata addresses are refused)
- `packages/core/src/consent.ts` (the existing record of who agreed to probing checks and when)
- `packages/core/src/checks/gated-download-open.ts` (the model for a probing check: off without
  consent, one request per address, a body read capped at 1,024 bytes, the query string never
  printed)
- `packages/core/src/checks/images/refs.ts` (the one place that already reads `/_next/image`
  addresses from a page)
- `packages/core/src/__tests__/post-boundary.test.ts` (no file but the allowed ones sends anything
  but a `GET` or a `HEAD`, so the probe cannot be a `POST`)
